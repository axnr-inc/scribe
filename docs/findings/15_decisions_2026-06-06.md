# Decisions snapshot — 2026-06-06

User-confirmed direction changes after the 3-bench pilot synthesis.

## Decision 1: LiveSQLBench — deferred

**Decision:** Drop LiveSQL from active experiments until a separate text-to-SQL harness variant is designed. Keep `configs/livesql_scribe.yaml`, prompts, adapter, and grader on disk (no deletion) — just stop running it in pilots.

**Rationale (from `14_paradigm_fit_and_helper_strategy.md`):**

1. **Paradigm-fit mismatch.** SCRIBE is built for docs-heavy iterative computation (DABStep, Krama). LiveSQL is text-to-SQL — the output is a single SQL query, the DB executes, no iterative refinement. SCRIBE's ReAct loop + cascade is structurally sub-optimal for this paradigm.

2. **Empirical confirmation.** 1/10 pilot, 6 SPEC_WRONG verdicts that didn't converge (virtual_10 hit the 3-revision cap), the only PASS was the simplest spec (crypto_8, 3 CTEs / 1 KB formula).

3. **Honest paper framing.** Leading with "docs-heavy iterative computation" lets us amplify our strongest result (Krama 42% matching smolagents-DR with weaker base models). Including LiveSQL forces us to defend a 10% number we don't have the architecture to fix without a separate research project.

4. **Right architecture for LiveSQL** is closer to AlphaCodium (test-anchored iterative SQL refinement) or Snowflake Cortex Analyst (deterministic compile + verified-query retrieval) — not the SCRIBE cascade.

**What this changes:**
- Pilots and experiments going forward: DABStep + Krama only
- LiveSQL config / prompt / adapter / grader stay on disk for future reactivation
- Paper framing: "SCRIBE for docs-heavy iterative computation" with LiveSQL as a follow-up paper
- Cross-benchmark fairness numbers in `02_cross_benchmark_fairness.md` need a footnote

## Decision 2: Krama HELPER_MANIFEST — build paradigm-level helpers

**Decision:** Build `data/context/krama_helper.py` with paradigm-level pandas patterns (NOT DABStep-style domain helpers). Wire into `extract_specs_krama.py`'s SYSTEM_PROMPT and into the executor's REPL preamble.

**Rationale:**
- Fair cross-benchmark comparison requires Krama to have helpers if DABStep does
- 5 of 7 Krama pilot failures map directly to common paradigm patterns (multi-header xlsx, dedup, interpolation, BP conversion, missing-marker handling)
- DABStep-style domain helpers don't translate (Krama has 6 different scientific domains; no shared business semantic)
- BUT cross-domain patterns DO translate — they encode common data-cleaning bugs

**Helpers shipped (5):**
- `read_multi_header_excel(path, sheet, header_keywords)` — fixes hard-2 wet-dry index column
- `parse_missing_marker(df, cols, markers)` — fixes Krama paper's "M means missing"
- `safe_dedupe(df, keys, agg)` — fixes hard-12 conflict over-count
- `linear_interp_by_key(df, key_col, value_col)` — fixes hard-1 Potassium interpolation
- `bp_to_calendar_year(years_bp, reference_year=1950)` — fixes hard-5 Neolithic year

**File:** `data/context/krama_helper.py`. Functional smoke-test passed.

**Sequencing:**
- File created NOW (independent of P2b agent's edits)
- Wiring into `extract_specs_krama.py` SYSTEM_PROMPT — WAIT for P2b agent to complete (same file)
- Wiring into executor's REPL preamble — wait for P2b (touches run.ts preamble logic)

**Expected lift:** +3-5% on Krama pilot (1-2 additional task PASSes out of 12). Lower than DABStep's HELPER_MANIFEST lift because Krama's domain divergence limits cross-task reuse, but addresses real failures we observed.

## Decision 3: Use Fireworks2 (FIREWORKS_API_KEY2) — and shard across both keys

**Decision:** Switch primary configs to `provider: fireworks2` for faster inference; add sibling `*_fw1.yaml` configs for `provider: fireworks` (primary key) so we can shard parallel pilot runs.

**Why:** User reports Fireworks2 has better inference latency. Plus, having 2 keys means we can split a 20-task pilot into 2×10-task runs in parallel without rate limits.

**Configs:**
- `configs/scribe_main.yaml` — uses fireworks2 (primary going forward)
- `configs/scribe_main_fw1.yaml` — uses fireworks (sibling for sharding)
- `configs/kramabench_scribe.yaml` — uses fireworks2
- `configs/kramabench_scribe_fw1.yaml` — uses fireworks (sibling)

**Usage pattern for sharding:**

```bash
# Shard DABStep pilot across both keys
head -5 data/splits/dabstep_pilot10.jsonl > /tmp/dabstep_half_a.jsonl
tail -5 data/splits/dabstep_pilot10.jsonl > /tmp/dabstep_half_b.jsonl

# Run both halves in parallel
npx tsx src/run.ts -d /tmp/dabstep_half_a.jsonl -c configs/scribe_main.yaml      -o results/dabstep_pilot10_v2_a --specs results/dabstep_pilot10/specs -n half_a &
npx tsx src/run.ts -d /tmp/dabstep_half_b.jsonl -c configs/scribe_main_fw1.yaml  -o results/dabstep_pilot10_v2_b --specs results/dabstep_pilot10/specs -n half_b &
wait

# Merge results
mkdir -p results/dabstep_pilot10_v2
cp -r results/dabstep_pilot10_v2_a/* results/dabstep_pilot10_v2/
cp -r results/dabstep_pilot10_v2_b/* results/dabstep_pilot10_v2/

# Grade
PYTHONPATH=vendor/dabstep_scorer python3 scripts/grade.py --out results/dabstep_pilot10_v2 --gold data/verified_answers.json
```

Same pattern for Krama (split krama_archeology12 into 2 × 6).

**Effective throughput:** roughly 2× faster pilot runs (assumes both keys are rate-limited independently).
